# 任务执行规则

## 开工前

1. 确认任务状态真值：`gh issue list`（任务包体系已归档，Issue 是唯一真值）。
2. 只读当前 Issue + 它显式列出的参考文件。不要顺手读全部 `docs/*.md`，不要顺手做邻近任务。
3. **验收标准本身是待验证断言**：先核对里面的数字与边界条件再动手；发现偏差按安全边界实现，
   并在 Issue 里写明偏离理由（#68 两次靠这个挡住了照字面执行的错误）。
4. **删除类任务先列消费者清单再动手**：对被删名字做全仓 grep（至少覆盖源码、README、docs、
   tests、`.ts`、`.mjs`、`.sh`），不能只看 import 图；subprocess、shell 与动态引用同样是消费者。
   再做双向检查（入边：谁依赖它；出边：删完之后谁还用它）。成本 30 秒，省三轮往返（#68、#74）。
   静态分析生成的消费者清单或映射表，必须先从原始文件抽样核对，再用于删除决策；不得直接把
   工具输出当成事实。
5. **一次接多个 Issue 先做文件重叠矩阵**：无重叠的就并行，不要把「串行」当规则照抄；
   「会被后续每一步复用」的元工具改进（如验证加速）最先做（#68 前后半程效率差 6 倍的主因）。

## 原子性

**一个任务只能改变一个行为面。** 需要同时改两个以上行为面就必须拆分。

- ✅ 合格：config schema 校验 / runner fake executor 边界 / snapshot summary 聚合 / Swift snapshot decode
- ❌ 不合格：「重构 collector 并改 Widget」/「把 UI 做完整」/「实现所有 limits 功能」

任务范围在执行中变大时**停下并报告**，不要擅自扩大。需要后续工作就新开 Issue，不在原任务里膨胀。

## TDD：先红后绿

1. 先写失败测试或 contract fixture。
2. **实际运行确认它失败，且失败原因是目标行为缺失**（不是导入错误、路径写错）。
3. 写最小实现。
4. 跑任务要求的最小测试。
5. 跨层影响时跑 `scripts/verify.sh` 全量。

**不允许**为了让测试通过而弱化断言、改预期值或缩小验收。
文档类任务可以不写代码测试，但必须有 grep / diff / 链接检查等可执行的文档验收。

新测试必须可离线 fixture 重放：纯标准库 `unittest`，无网络、无真实 `ccusage`/SSH/provider。

守恒、恒等式或口径一致性类交付，必须增加一条**直接读取最终产物并独立复算**的测试；复算不得
调用被测实现的 helper、聚合器或断言。#89 的 provider slots parity 是最低判例：实现和测试共享
同一心智模型时都会绿，只有从产物正交复算才能发现静默丢失。

## 收口交付

必须回报：

- 改了哪些文件
- 跑了哪些测试、结果如何（用 `scripts/verify.sh` 的输出）
- **每个行为面的「先红」证据**：跑了什么命令、红在哪一行、错误信息是什么。
  红的原因必须是目标行为缺失，不是导入错误或路径写错。
- **新增守卫的变异证据**：故意破坏它守护的东西 → 它变红的实际输出。
  只说「现在是绿的」不算数（判例集见 `.claude/rules/tests.md`）。
  变异分两步：**先确认注入真的生效**（看到预期的红，或打印注入后的实际值），再谈还原回绿。
  绿有两种含义（守卫有效 / 注入没生效），二者无法区分——红才是变异证据（#68 差点因此得出错误结论）。
- **哪些测试没跑，以及原因**（尤其是本机不可验证、需回 Mac 侧的项）
- 是否触碰了任务范围之外的内容
- 是否需要新开后续 Issue
- 当前证据等级（调用 `/verify` 对齐）

实现完成后收口前，用 `reviewer` subagent 在干净上下文审一遍 diff。

派 subagent 委托工作时：报告里要求一节「**意外事实**」（#68 三个新 Issue 全来自这一节）；
报告与审查意见里的**关键事实是待验证断言**，逐条实测复核后才能作为决策依据
（#68 一轮里挡下四次错误结论，包括一次会炸掉生产部署的审查建议）。
并行 subagent：临时产物用各自唯一前缀，禁止修改仓库级 git config；并行分支合并后必须在
合并结果上重跑测试，不能拼接各分支各自的绿色结论。

**没有用户明确要求，不得 `git add` / `git commit` / `git push`。**
