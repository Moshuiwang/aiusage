# 交付复盘

对刚完成（或指定）的一段工作做复盘，产出写进 GitHub Issue #68（本仓库的复盘专用 Issue）的评论。

**参数**：$ARGUMENTS —— 可以是 Issue 号、commit 范围、或留空（默认复盘本次会话）。

## 这个复盘要回答什么

**不是**「解决了哪些问题」。成果在 Issue、PR 和 commit 里已经写过了，重复一遍没有价值。

要回答的是：**方法有没有搞错，因此多花了多少时间和用量。**

具体三问：

1. **时间和 token 去哪了** —— 要量化到「哪一步花了多久 / 跑了多少次」，不要「花了不少时间」。
2. **哪些是方法错误，不是知识错误** —— 知识错误（不知道某个 API）不值得复盘，下次查就行。
   方法错误（明明记录过还再犯、验证方式本身有漏洞、判断顺序反了）才值得。
3. **哪些路线是白走的** —— 走进去又退出来的分支，退出来的原因是什么，事前能不能避免。

## 采集素材（先做，别凭印象写）

```bash
# 1. 时间跨度与提交节奏
git log --format="%h %ad %s" --date=format:"%H:%M" <范围>

# 2. 改动规模（区分「实现」与「返工」）
git log --stat <范围> | tail -40

# 3. 测试规模变化 —— 新增测试数 vs 新增实现行数，比例失衡本身是信号
git diff --stat <起点>..HEAD -- tests/ src/ cloudflare/

# 4. 本轮开的 Issue —— 哪些是「顺带发现」，说明原计划的盲区在哪
gh issue list --state open --limit 20 --json number,title,createdAt

# 5. 恢复卡 / auto memory 里记过的坑
cat ~/.claude/projects/*/memory/*.md 2>/dev/null | grep -A 3 -iE "坑|教训|踩"
```

## 必须覆盖的检查项

逐条回答，**没有就写「无」，不要跳过**：

- [ ] **重复踩的坑**：同一个错误犯了几次？第一次之后做了什么补救、为什么没生效？
      （文字记录对「当场要用的手法」通常无效——需要换掉手法本身，不是记住它）
- [ ] **假绿 / 假阴性**：有没有出现过「测试绿了但结论错」「查不到就当不存在」？
      根因是判据选错、还是验证方式本身有漏洞？
- [ ] **返工**：有没有做完又推翻的？推翻的理由在动手前能不能知道？
- [ ] **等待与并发**：有多少时间在等？等的过程中有没有可并行而没并行的？
      并行了的有没有互相踩？
- [ ] **工具与流程开销**：验证一次要多久、跑了几次、其中几次是必要的？
      有没有「元工具」（能让后续每次都变快的改进）本该更早做？
- [ ] **委托质量**：交出去的任务，回来的结果里有多少需要返工/复核？
      失败的委托是怎么失败的（挂了？跑偏了？还是交付了但事实错了）？
- [ ] **契约与验收标准本身的错误**：有没有发现「按字面执行会出问题」的验收标准？
      是怎么发现的——主动核实还是被测试打脸？
- [ ] **做对了什么**（要具体，为了保留）：哪些做法实际挡住了事故？证据是什么？

## 一条反复出现的模式，优先查它

**「执行了动作」≠「达成了效果」。**

本项目 AGENTS.md 对业务交付强调过这条（按钮点了、任务返回成功、端口开放、文件存在，
都不自动代表交付）。但它在**自己的操作层面**同样成立，而且更容易被忽略：

- `rm -rf <path>` 打了「已删除」，但删的是错的路径 → 后续「无事可做」被当成成功
- `fuser -k <port>` 打了「已停止」，但只杀了监听端口那一个，父进程链还活着
- agent 报告「已还原」，但实际残留在工作区
- 变异注入了，但判据写错、根本没生效 → 测试绿被误读成「守卫有效」

复盘时逐个动作问：**做完之后有没有回读确认？** 没有回读的地方，就是下次出问题的地方。

注意：**改法通常不是「换一个命令」，而是「加一道回读」**。换命令只是把一种失败模式
换成另一种（本轮就发生过：把 `pgrep -f` 换成 `fuser -k`，40 分钟后被证伪）。

## 资源盘点已机制化

收口资源盘点、`pkill -f` / 坏等待循环的拦截已由机制承担（`scripts/stop_gate.sh` 的残留进程
检查 + `scripts/bash_guard.sh` PreToolUse 门禁 + CLAUDE.md 的 TaskStop 纪律），不再靠文字提醒。
复盘时只需检查：**这些机制本轮有没有被触发过？触发时给出的替代手法有没有被采纳？**
机制没拦住的新失败模式，才是本节要写的内容。

## 写作要求

- **量化优先**：「verify 全量单次 8-13 分钟，跑了 7 次，其中 3 次不必要」远好于「验证花了很多时间」。
- **根因要往下挖一层**：不是「我忘了」，而是「为什么这个信息在需要它的时刻没有出现在我面前」。
- **区分「该做没做」和「做了但方式错」**：前者是遗漏，后者是方法问题，改法完全不同。
- **不要为了显得深刻而编根因**。拿不准就写「未知，需要下次观察 X」。
- **对做对的部分同样具体**。只写问题会导致下次把对的一起改掉。

## 产出

写成 Markdown，用 `gh issue comment 68 --body-file <file>` 发到 #68。

结构建议：

```
## 一、这次花了多少（量化）
## 二、方法错误与根因（每条：现象 → 根因 → 改法）
## 三、白走的路线（每条：为什么走进去、怎么退出来、事前可否避免）
## 四、做对了什么（要保留的）
## 五、下次改什么（可执行的，不是口号）
```

第五节的每一条都要能落到具体动作：改哪个脚本、加哪条断言、换掉哪个手法。
写不出具体动作的，说明根因还没挖到底。
